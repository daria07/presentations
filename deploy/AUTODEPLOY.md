# Автодеплой: выкладка по пушу в main

После настройки руками на сервер ходить не нужно. `git push` в `main` →
GitHub Actions прогоняет проверки → если они зелёные, заходит на сервер по SSH
и запускает тот же `deploy/deploy.sh` → проверяет, что сайт ответил.

Настраивается один раз, занимает минут пятнадцать. Дальше — ничего.

Обозначения: `СЕРВЕР` — IP или домен VPS. Где сказано «на сервере под root» —
это `ssh root@СЕРВЕР`.

---

## Как это устроено

Два файла в `.github/workflows`:

| Файл         | Когда запускается                                                       | Что делает                                                                  |
| ------------ | ----------------------------------------------------------------------- | --------------------------------------------------------------------------- |
| `tests.yml`  | пуш в `main`, любой pull request                                        | `composer ci:check`: Pint, PHPStan, Pest, `vp check`                        |
| `deploy.yml` | после того как `tests` завершились **на ветке main**, и вручную кнопкой | заходит по SSH и выполняет `cd /var/www/slaidusha && bash deploy/deploy.sh` |

Важные свойства:

- **Красная сборка на сервер не едет.** `deploy.yml` проверяет
  `conclusion == 'success'` и при провале просто не стартует.
- **Pull request ничего не выкладывает.** У `deploy.yml` стоит фильтр
  `branches: [main]`, а запуск тестов из ветки с PR идёт по другой ветке.
- **Две выкладки одновременно невозможны.** `concurrency` ставит вторую в
  очередь, а не запускает рядом: иначе два `git pull` дрались бы за один
  каталог.
- **После выкладки сайт проверяется.** Шаг стучится в `https://slaidusha.ru/up`
  до десяти раз с паузой 6 секунд. Не ответил 200 — выкладка помечается
  провалившейся, и GitHub присылает письмо.

`deploy/deploy.sh` остаётся прежним и никуда не девается: workflow только
вызывает его. Если GitHub недоступен, всё так же работает ручной путь —
`ssh deploy@СЕРВЕР`, `cd /var/www/slaidusha`, `bash deploy/deploy.sh`.

## 1. Ключ для GitHub (на своём компьютере)

Отдельный ключ, не тот, которым заходишь сама: его можно отозвать, не трогая
собственный доступ.

```bash
ssh-keygen -t ed25519 -C "github-actions-deploy" -f ~/.ssh/slaidusha_deploy -N ""
```

Получились два файла: `~/.ssh/slaidusha_deploy` (приватный, он пойдёт в секреты
GitHub) и `~/.ssh/slaidusha_deploy.pub` (публичный, он пойдёт на сервер).

`-N ""` — без пароля на ключ. Пароль здесь не нужен: вводить его некому,
Actions работает без человека.

---

## 2. Публичный ключ на сервер

Показать публичный ключ:

```bash
cat ~/.ssh/slaidusha_deploy.pub
```

Это одна строка вида `ssh-ed25519 AAAA… github-actions-deploy`. Скопировать
её целиком.

На сервере под root:

```bash
mkdir -p /home/deploy/.ssh && chmod 700 /home/deploy/.ssh
nano /home/deploy/.ssh/authorized_keys
```

Вставить строку **новой строкой в конец файла**, ничего не удаляя: там уже
лежит ключ, которым ты заходишь сама. Сохранить (`Ctrl+O`, `Enter`, `Ctrl+X`).

```bash
chmod 600 /home/deploy/.ssh/authorized_keys
chown -R deploy:deploy /home/deploy/.ssh
```

Проверить, не ограничен ли список тех, кому можно заходить:

```bash
grep -E "^AllowUsers|^PasswordAuthentication|^PubkeyAuthentication" /etc/ssh/sshd_config
```

Если строки `AllowUsers` нет — всё в порядке, ничего не трогаем. Если есть и
в ней нет `deploy` — дописать его через пробел и перечитать конфиг:

```bash
systemctl reload ssh
```

**Не закрывай сессию root, пока не проверишь следующий шаг.**

---

## 3. Проверка доступа

Со своего компьютера:

```bash
ssh -i ~/.ssh/slaidusha_deploy deploy@СЕРВЕР 'whoami && cd /var/www/slaidusha && git status --short --branch'
```

Ожидаем `deploy` и `## main...origin/main`. Если вместо этого просят пароль —
ключ не подхватился: проверь права (`700` на `.ssh`, `600` на
`authorized_keys`), владельца (`deploy:deploy`) и что строка вставлена целиком,
без переносов.

Заодно убедись, что сервер сидит на `main`: `deploy.sh` делает
`git pull --ff-only`, и с другой ветки выкладка просто не поедет.

---

## 4. Отпечаток сервера

Чтобы Actions знал, к какому именно хосту подключается, и не отдал приватный
ключ подставному:

```bash
ssh-keyscan -t ed25519 СЕРВЕР
```

Вывод — строка вида `СЕРВЕР ssh-ed25519 AAAA…`. Строки, начинающиеся с `#`,
не нужны.

Сверить её с настоящим ключом сервера (на сервере под root):

```bash
cat /etc/ssh/ssh_host_ed25519_key.pub
```

Часть `AAAA…` должна совпасть. Если нет — не продолжай, разберись почему.

---

## 5. Секреты в GitHub

Репозиторий → **Settings** → **Secrets and variables** → **Actions** →
**New repository secret**. Пять штук (пятый — только при нестандартном порте):

| Имя                  | Что положить                                                                                |
| -------------------- | ------------------------------------------------------------------------------------------- |
| `DEPLOY_SSH_KEY`     | вывод `cat ~/.ssh/slaidusha_deploy` целиком, вместе со строками `-----BEGIN…` и `-----END…` |
| `DEPLOY_HOST`        | IP или домен сервера                                                                        |
| `DEPLOY_USER`        | `deploy`                                                                                    |
| `DEPLOY_KNOWN_HOSTS` | строка из шага 4                                                                            |
| `DEPLOY_PORT`        | номер порта SSH, если он не 22; иначе секрет не создавать                                   |

Секреты видны только Actions: после сохранения их нельзя прочитать даже тебе,
можно только перезаписать.

---

## 6. Окружение production

Репозиторий → **Settings** → **Environments** → **New environment** → имя
`production` → Configure.

Само окружение нужно, чтобы выкладки были видны отдельной лентой на главной
странице репозитория. Дополнительно там можно включить:

- **Required reviewers** — тогда после зелёных тестов выкладка будет ждать
  твоего нажатия «Approve». Полезно, если не хочется, чтобы код уезжал на
  прод, пока ты не смотришь.
- **Deployment branches** — ограничить выкладку веткой `main`, на случай
  случайного запуска из другой ветки.

---

## 7. Первый запуск

`deploy.yml` должен сначала оказаться в `main` — GitHub берёт workflow из той
ветки, на которой он лежит. То есть первый пуш этот файл только доставит, а
сработает он со следующего.

Проще проверить руками, не дожидаясь: вкладка **Actions** → слева workflow
**deploy** → **Run workflow** → ветка `main` → **Run workflow**.

Что должно получиться:

```
✓ Подключаем ключ
✓ Выкладываем           ← здесь виден весь вывод deploy.sh
✓ Проверяем, что сайт поднялся
```

## Если что-то пошло не так

**`Permission denied (publickey)`** — Actions не пустили на сервер. Проверь
`DEPLOY_USER` (должен быть `deploy`, не `root`), что в `DEPLOY_SSH_KEY` лежит
**приватный** ключ со строками BEGIN/END, и что публичный ключ действительно
попал в `/home/deploy/.ssh/authorized_keys`.

**`Host key verification failed`** — не сходится `DEPLOY_KNOWN_HOSTS`. Если
сервер переустанавливали, у него новый ключ: повтори шаг 4 и перезапиши секрет.

**Выкладка прошла, а сайт не ответил** — шаг проверки красный. Зайди на сервер
и посмотри:

```bash
ssh deploy@СЕРВЕР
cd /var/www/slaidusha
php artisan up                 # вдруг приложение осталось в режиме обслуживания
tail -50 storage/logs/laravel.log
sudo tail -50 /var/log/nginx/error.log
```

**Нужно откатиться** — вернуть предыдущий коммит и выложить заново:

```bash
ssh deploy@СЕРВЕР
cd /var/www/slaidusha
git log --oneline -5           # найти последний рабочий коммит
git reset --hard <хеш>
bash deploy/deploy.sh
```

После этого верни `main` в GitHub в то же состояние (`git revert`), иначе
следующая же выкладка вернёт сломанный код.

**Отозвать доступ** — удалить строку с `github-actions-deploy` из
`/home/deploy/.ssh/authorized_keys` на сервере. Своего доступа это не затронет.

## Что держать в голове

- Приватный ключ живёт в двух местах: секреты GitHub и твой компьютер. В
  репозиторий он не попадает никогда.
- Ключ даёт полный вход под `deploy`, а у него лежит `.env` с ключом шлюза и
  паролем базы. Доступ к репозиторию = доступ к серверу, так что к тому, кого
  пускаешь в репозиторий, отношение такое же, как к тому, кого пускаешь на
  сервер.
- Миграции накатываются автоматически внутри `deploy.sh`. Необратимые —
  удаление колонки, переименование таблицы — лучше выкладывать, когда ты
  рядом и можешь посмотреть на результат.
